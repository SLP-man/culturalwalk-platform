# ADR-0003：四套状态机分离，发布绑定具体版本 hash

- 状态：已接受
- 日期：2026-10-26
- 决策者：P1、P2

## 背景

投稿审核最容易出的事故类型是"审的和发的不是同一份内容"：作者在被审期间改了内容，或者审核通过后作者又改了一版，结果线上出现了没人审过的内容。

## 决策

用四套**互不复用**的状态机，各自有独立的字段和迁移函数：

| 状态机 | 状态集 | 谁推进 |
|---|---|---|
| 草稿 `route_draft.state` | EDITING / SUBMITTED / SUPERSEDED | 作者 |
| 投稿 `submission.state` | SUBMITTED / RESUBMITTED / APPROVED / REJECTED / WITHDRAWN | 作者 + 审核员 |
| 审核任务 `review_task.state` | OPEN / CLAIMED / COMPLETED / CANCELLED | 审核员（含租约超时回收） |
| 发布 `publication.state` | PUBLISHED / UNPUBLISHED | 编辑 |

关键规则：

1. 提交审核时**冻结**内容为不可变 `route_version`，并计算 `content_hash`。
2. 审核决定记录 `reviewed_version_id` + `reviewed_hash`。
3. 发布请求必须带上 `version_id` 和 `content_hash`，与记录不一致则 409。
4. 已 CLAIMED 的稿子作者不能撤回（否则审核员的 diff 会变），只能由审核员释放或租约到期。
5. 作者在 SUBMITTED 期间修改 → 生成新草稿，旧投稿标 SUPERSEDED。

## 理由

- 状态集分离让"能不能做这个操作"变成一个查表问题，而不是散落各处的 if 嵌套。
- 版本 + hash 是唯一能证明"审的就是发的"的机制，比"审核通过后锁定编辑权限"更可靠（后者可以被后台脚本绕过）。

## 后果

- 好：答辩时能直接演示"审核后改内容 → 发布失败 → 409"这个负例，说服力比讲设计强。
- 坏：多一次快照写入，草稿与版本要双写。**对策**：快照只在提交时生成一次，Draft 与 Version 用同一事务。
- 坏：状态迁移函数变多。**对策**：统一写在 `service.py` 的显式函数里（如 `freeze_version`、`publish`），并在测试里覆盖每条边。
