# ADR-0001：采用模块化单体，而不是微服务

- 状态：已接受
- 日期：2026-10-26
- 决策者：P1（架构）、P2（后端）、指导老师

## 背景

本期目标是能跑通、能答辩、能被 5–8 人并行开发的一个中等规模 Web 应用：路线浏览、投稿审核、行程规划三条链。团队是学生，没有人维护过分布式系统；部署环境是一台服务器 + 一个数据库。

## 决策

**一个后端进程、一个数据库、一个前端应用**，内部按业务模块物理分目录（`app/modules/<模块>/`），模块之间只能通过 `service.py` 暴露的函数调用，不允许跨模块直接 `import models`。

## 理由

1. 8 周的有效开发时间里，微服务带来的服务发现、链路追踪、分布式事务、多份部署脚本都是纯成本，换不来任何用户可见的功能。
2. 审核流要求"同一事务内改状态 + 写审计 + 发通知"，单体一个事务就能保证；拆服务就得引入 outbox 或 saga，是典型的自找麻烦。
3. 模块边界用目录和 import 规则表达，已经足够 8 个人并行；真要拆，后端的 `service` 函数天然就是未来的 RPC 边界。

## 后果

- 好：部署简单（compose 两个进程）、事务简单、调试简单、新人上手快。
- 坏：模块边界靠纪律（code review + ruff 规则 + 目录约定）而不是网络边界强制的。**对策**：`docs/00` 第 4 节写死依赖方向，评审清单里逐条检查，违反的 PR 直接打回。
- 坏：单进程内的长任务（AI 规划）会占资源。**对策**：`planner` 走"提交即返回 202 + worker 异步跑"的形态，接口按异步设计，将来拆出去不用改前端。

## 什么情况下重新考虑

同时满足三条才拆：① 单库写入成为瓶颈（有监控数据）② 某个模块需要独立扩容 ③ 团队里有人能长期负责运维。任缺一条都不拆。
