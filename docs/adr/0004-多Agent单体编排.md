# ADR-0004：多 Agent 放在单体进程内编排，不做分布式

- 状态：已接受
- 日期：2026-10-26
- 决策者：P1、P4

## 背景

产品要求"多 Agent 协同规划"，并且要有可解释的过程（哪一步做了检索、哪一步发现超预算）。团队里容易出现的误解是"多 Agent 就是要多个服务/多个进程互相发消息"。

## 决策

四个 Agent（`researcher` → `planner` → `critic` → `verifier`）实现为**同一进程里的四个类**，共用 `PlanContext`，由 `PlannerService` 顺序编排；每次执行把每一步的输入摘要、输出、耗时、错误写进 `agent_step` 表。

- 步骤失败：`run.state = FAILED`，已完成步骤的结果保留，不整体回滚。
- 外部模型/地图调用：通过 `Provider` 适配器，`fake` 实现可离线跑通演示。
- 并发：一次请求 = 一个 `plan_run` 行；worker 用 `FOR UPDATE SKIP LOCKED` 抢任务。

## 理由

1. "Agent"的本质是**职责分离 + 可观测的过程**，不是网络拓扑。四个类一样能做到，还能共享数据库连接和上下文对象。
2. 分布式编排要处理序列化、超时、重试、幂等、消息丢失，这些在答辩期间全是不可控风险。
3. 步骤表让 UI 能显示"第 2 步：按距离重排，耗时 320ms"，这比画一个花哨的架构图更能证明"多 Agent 在工作"。

## 后果

- 好：一次规划在一个进程内跑完，调试只需看一个日志文件；离线可演示。
- 好：将来真要拆，每个 Agent 的输入输出已经是 `PlanContext` 的纯数据，切成 RPC 不难。
- 坏：单进程内跑慢模型会占 worker。**对策**：HTTP 提交立即返回 202，worker 异步执行，前端轮询 `GET /plans/{id}` 看进度。
- 坏：容易写成"四个函数串起来"而失去职责边界。**对策**：约定每个 Agent 只做一件事、不许互相 import，`critic` 只能读 `planner` 的输出、不许改它。
