## 1. 一句话说清产品

CulturalWalk = **文化路线平台**，两条并列主链：

1. **规划**：用户给「城市 + 天数 + 人数 + 预算 + 偏好」→ 系统（多 Agent 编排）输出一条带时间、顺序、费用区间、文化说明的**行程**，可保存、可分享。行程是**用户私有**的，不自动进社区。
2. **共创**：用户（作者）写**路线** → 提交审核 → 管理员发布 → 匿名可见可搜可收藏可评论。发表内容一律有来源、有审核。

首版只做**长沙**单城。技术基线：`Vue 3 + TS` 前端 / `FastAPI + SQLAlchemy 2 + PostgreSQL 16` 后端 / `MinIO` 媒体 / **模块化单体**（一个进程、一个库、模块间只走 service 函数）。

## 2. 目录与命令

```
culturalwalk-platform/
├─ apps/web/                   前端（Vue3 + Vite + TS，移动优先）
├─ services/api/               后端
│  ├─ app/main.py              唯一入口，装 router
│  ├─ app/core/                配置/DB/session/错误/日志/依赖注入
│  └─ app/modules/<模块>/      每个模块固定 5 个文件，见 §4
├─ packages/contracts/         由 openapi 生成的 TS 类型（生成物，勿手改）
├─ docs/api/openapi.yaml       ★ 接口唯一事实源
├─ tasks/cards.yml             任务卡（脚本生成，勿手改）
├─ scripts/                    生成/校验脚本
└─ infra/                      docker-compose、部署
```

| 目的 | 命令（在仓库根执行） |
|---|---|
| 一键起数据库等 | `docker compose -f infra/docker-compose.yml up -d` |
| 后端依赖 | `cd services/api && python -m pip install -e ".[dev]"` |
| 后端测试 | `cd services/api && python -m pytest -q` |
| 后端 lint | `cd services/api && ruff check . && ruff format --check .` |
| 起后端 | `cd services/api && uvicorn app.main:app --reload --port 8000` |
| 前端依赖 | `pnpm install`（**在仓库根**，workspace 统一装） |
| 前端类型检查 | `pnpm typecheck` |
| 前端开发 | `cd apps/web && pnpm dev` |
| 生成 TS 类型 | `pnpm contracts:gen`（读 openapi.yaml） |
| 校验接口/卡/类型一致 | `pnpm contracts:check` / `pnpm cards:check` |

CI 会跑：后端测试+lint、前端 typecheck+build、契约一致、compose 配置合法。**本地先跑绿再推。**

## 4. 每个模块的固定形状

```
app/modules/<模块>/
├─ models.py     SQLAlchemy 表（只属于本模块）
├─ schemas.py    Pydantic 入参/出参（对外形状以 openapi.yaml 为准）
├─ service.py    业务逻辑，纯函数优先，不碰 HTTP
├─ router.py     APIRouter，只做：验参 → 调 service → 返回
└─ __init__.py   导出 router
```

新模块复制任一现有模块即可（`identity` 最完整）。

## 5. 接口硬规则（10 条，违反就返工）

1. 前缀 `/api/v1`；**接口唯一事实源** `docs/api/openapi.yaml`。**改接口 = 先改 yaml → 提 PR → 通知前端**，不许后端先写完再说。
2. 认证：`Authorization: Bearer <token>`；access 15 分钟、refresh 14 天且轮换；未登录 `401`、无权限 `403`，不许混用。
3. 所有 `POST`（注册/登录除外）必带 `Idempotency-Key: <uuid>`，同 key 重放返回首次结果，服务端存 24h。
4. 编辑类 `PATCH` 必带 `If-Match: <lock_version>`，不匹配回 `412`。
5. 错误体固定：`{"error":{"code","message","request_id","details"}}`；`code` 用大写下划线，前端按 `code` 分支，**不许按 message 文案判断**。
6. 分页一律游标：`?cursor=&limit=`，返回 `{"items":[],"next_cursor":null}`，不用 offset。
7. ID 用 ULID 字符串；时间一律 UTC ISO-8601（带时区），展示时才转本地。
8. 金额用「分」的整数 + 币种，禁止 float。
9. 公开读接口只能读**已发布**内容；草稿、审核中、已下线一律 404（不泄露存在性）。
10. 任何写操作都要落 `audit_logs`（谁、何时、对什么、前后状态）。

## 6. 四套状态机（互不复用，别硬套）

| 状态机 | 允许的流转 | 谁能推 |
|---|---|---|
| 路线草稿 `route_draft` | `DRAFT → SUBMITTED →（APPROVED/PUBLISHED）/ REJECTED / SUPERSEDED` | 作者提交；审核决定；fork 产生新草稿时旧的 `SUPERSEDED` |
| 投稿 `submission` | `PENDING → CLAIMED → APPROVED / REJECTED / RESUBMITTED`；`CLAIMED → PENDING`（释放/租约过期） | 作者提交/撤回（未认领时）；审核员认领与决定 |
| 审核任务 `review_task` | `OPEN → CLAIMED → COMPLETED / CANCELLED`；`COMPLETED` 只表示**审核动作结束**，不代表通过 | 审核员 |
| 发布 `publication` | `DRAFT → SCHEDULED → PUBLISHED → WITHDRAWN` | 管理员 |

**核心不变量**：草稿提交那一刻序列化成 JSON 并算 `content_hash`，之后**不可改**；审批针对**这个 hash**；发布记录的也是这个 hash。要改内容 → fork 新草稿（旧的变 `SUPERSEDED`）。

## 7. 数据与迁移

- 表在各自模块 `models.py`；迁移用 Alembic，**一个 PR 一份迁移**，`upgrade` 必须可重放（幂等）。
- 外键：跨模块只允许引用 `users.id`（身份是所有内容的作者锚点）；其余跨模块关联用 ID 字段 + service 校验，不建物理外键。
- 删除：内容一律软删（`deleted_at`），媒体走 `WITHDRAWN`。
- 每个事实性字段（开放时间、票价、来源）都要能追到 `place_sources`；**没来源的事实不许进公开内容**。

## 8. 写代码的规矩

- 命名：Python `snake_case`、TS `camelCase`、文件 `kebab-case`；错误码 `UPPER_SNAKE`。
- 注释只写「为什么」，不写「是什么」；不写 `# TODO` 了事，要在卡里记。
- 不许裸 `print`（用 logger）；不许把密码/token 写进日志；不许 `timezone.now()` 不带 tz。
- 前端：所有接口调用走 `apps/web/src/api/`（由契约类型约束），页面里不出现 `fetch` 裸调。
- 依赖：加依赖要在 PR 里说明理由（体积、维护、许可证），不许为了省事引重型库。

## 9. 什么算「做完」（Definition of Done）

一张卡只有**全中**才算完：

1. 代码在新分支，`main` 没被动过；
2. 有测试：至少 1 个正向 + 1 个**负向**（例如「密码错必须 401」）；
3. 本地三绿：`pytest -q`、`ruff check .`、`pnpm typecheck`；
4. 接口若变了：`openapi.yaml` 同步改了，`pnpm contracts:check` 通过；
5. PR 描述里写了「这张卡对应 issue 号 + 怎么验收」；
6. PR 拿到 1 个 review 批准，CI 全绿。

## 10. 禁区（踩了会被打回）

- ❌ 跨模块 `import` 别人的 `models` / 直接读写别人的表。
- ❌ 绕过 openapi 先写后端，再让前端猜字段。
- ❌ 手改 `tasks/cards.yml`、`packages/contracts/*`（都是生成物）。
- ❌ 提交 `.env`、密钥、真实身份证/手机号等数据。
- ❌ 在 `main` 上直接提交（分支保护会拦）。
- ❌ 把 `AI 生成内容`直接当已审核内容发布。
- ❌ 为了过测试改测试断言（该改的是实现）。
- ❌ 引入「框架级」新依赖却不写 ADR。

## 11. 卡在哪、怎么认领

- 全部任务：`tasks/cards.yml`（57 张，含 `owner: P1~P4`、`depends_on`、`accept`）。
- 人看的版本：`docs/01-模块与任务看板.md` §1；GitHub Issues 同号（卡号↔issue 号见 `tasks/issues.csv`）。
- 认领：把 issue 的 Assignee 设成自己（或让 agent 代做）；认领后**先看 `depends_on`**，前置没做完就别开工。
- 不确定就**问**：在 PR 里写「这里我不确定，需要 lead 确认」，不要自己猜着写。
