## 0. 任务卡怎么写

每个任务在动手前，先在本文件对应行下面补三行（或写在 PR 描述里）：

```
输入：依赖谁的什么接口/契约
输出：我会新增/修改哪些文件
验收：跑什么命令、看到什么结果算完成
```

没有验收命令的任务不许开工。

## 2. 模块详解

### 2.1 identity

- **职责**：账号、会话、角色；给其他模块提供 `current_user` 依赖。
- **不做**：路线内容、审核判断、头像文件处理（交给 media）。
- **对外接口**：`require_user()`、`require_role("admin")`、`get_profile(user_id)`。
- **数据**：`users`、`sessions`。
- **注意**：密码用 Argon2id；token 短期 + refresh 轮换；退出即失效。

### 2.2 catalog

- **职责**：地点是「文化资料的载体」，路线只是引用它。一个地点可以出现在多条路线里。
- **不做**：决定路线顺序、决定发布。
- **关键字段**：`name`、`lat/lon`、`district`、`summary`、`culture_tags[]`、`open_hours`、`facts[]`。
- **来源模型**：每条 `PlaceFact` 必须挂 `PlaceSource`（URL/书名/口述），没有来源的事实不能进公开内容。

### 2.3 routes

- **职责**：草稿、节点、顺序、版本。
- **不做**：审核、发布、AI 生成。
- **版本规则**：草稿在提交那一刻序列化成 JSON + 计算 hash，之后不可改；要改只能 fork 新草稿。
- **费用**：每个节点可有 `price_range`，汇总时缺失项单独计数，不假装是 0。

### 2.4 planner

- **职责**：把「城市/天数/人数/预算/偏好」变成一条带时间与费用的行程。
- **不做**：直接发布、直接改路线。
- **四段式**：
  1. `Researcher`：从 catalog 检索候选地点与事实；
  2. `Planner`：按时间、地理邻近、预算组排；
  3. `Critic`：检查超预算、赶路、闭馆、重复；
  4. `Verifier`：逐项核对是否有来源，把没来源的标 `待核实`。
- **失败策略**：任一段失败 → run 标 FAILED 并保留已完成步骤；前端给「换个条件再试」而不是空白页。

### 2.5 discovery

- **职责**：所有「读」的聚合。只读，不写业务表。
- **不做**：任何写操作。
- **规则**：只查 current publication；`?status=` 一律忽略；未发布返回和不存在一样的 404。

### 2.6 community

- **职责**：评论、置顶、收藏。
- **不做**：改路线内容；举报申诉放二期。
- **注意**：评论要能应对「路线下线」——下线后评论保留但不展示。

### 2.7 moderation

- **职责**：审核队列、通过与退回、发布与下线、审计。
- **不做**：替作者改内容。
- **规则**：不能审自己的；退回必填理由；发布必须 hash 匹配；下线必须写原因。

### 2.8 media

- **职责**：上传、隔离、扫描、缩略图。
- **不做**：内容审核（那是 moderation 的事）。
- **演示期简化**：扫描可用「扩展名 + MIME + 大小」白名单代替杀毒，但接口形状保持真实，后续可替换。

### 2.9 notifications

- **职责**：站内通知。
- **不做**：短信、邮件、推送。

### 2.10 audit

- **职责**：只追加的审计流水。
- **不做**：业务逻辑。
- **字段**：`actor_id`、`action`、`object_type`、`object_id`、`before_hash`、`after_hash`、`reason`、`request_id`、`created_at`。

## 3. 三个示例任务卡（照这个粒度写）

### 示例一：RT-03 版本快照与 hash

```
目标：草稿提交时冻结成不可变版本，并计算内容 hash
输入：routes 模块的 RouteDraft + RouteNode 模型；MD-01 会调用
输出：
  services/api/app/modules/routes/service.py  (freeze_version)
  services/api/app/modules/routes/models.py   (RouteVersion)
  services/api/migrations/versions/xxxx_add_route_versions.py
  services/api/app/modules/routes/tests/test_freeze.py
验收：
  pytest services/api/app/modules/routes/tests/test_freeze.py -q  → 4 passed
  1) 同一草稿冻结两次，得到两个 version_id，hash 相同
  2) 改一个节点名再冻结，hash 不同
  3) 冻结后修改草稿，已生成的 version 内容不变
不在范围：状态机流转（MD-01）、hash 存哪张表以外的事
```

### 示例二：MD-01 提交事务

```
目标：作者点「提交审核」，一个事务内完成冻结版本 + 建投稿 + 建审核任务 + 写审计 + 锁草稿
输入：RT-03 的 freeze_version；ID-03 的 require_user
输出：
  modules/moderation/router.py   POST /api/v1/route-drafts/{id}/submit
  modules/moderation/service.py  submit_for_review()
  modules/moderation/tests/test_submit.py
验收：
  pytest .../test_submit.py -q  → 6 passed
  1) 成功：草稿变 SUBMITTED，投稿 SUBMITTED，任务 OPEN（名字以 ADR-0003 为准）
  2) 重复提交：第二次返回 409，不产生第二个版本
  3) 他人提交：403
  4) 模拟写审计失败：整个事务回滚，草稿仍是 EDITING
不在范围：审核动作本身（MD-03）
```

### 示例三：PL-03 多 Agent 编排骨架

```
目标：用固定接口串起 Researcher → Planner → Critic → Verifier，先跑通流程再接真模型
输入：catalog 的 search_places()；PL-01 的 PlanRun/AgentStep
输出：
  modules/planner/agents/base.py       Agent 协议：name / run(ctx) -> ctx
  modules/planner/agents/researcher.py
  modules/planner/agents/planner.py
  modules/planner/agents/critic.py
  modules/planner/agents/verifier.py
  modules/planner/orchestrator.py     顺序执行 + 记录每步耗时与状态
  modules/planner/tests/test_orchestrator.py
验收：
  pytest .../test_orchestrator.py -q  → 5 passed
  1) 四个 step 都被记录，顺序固定
  2) 某步抛异常 → run 状态 FAILED，已完成 step 保留
  3) 用 fake LLM 时全流程 < 1s
不在范围：真实模型调用（PL-04）、异步任务（PL-05）
```
