# 必读 2 · 零基础全流程（人看的）

> 你不需要会：命令行、Git、GitHub 的各种概念、写代码。
> 你需要会：**打字、点鼠标、判断"这个页面用起来对不对"**。
> 所有技术活都由 DSH 里的 agent 干，你负责**说清楚要什么**和**验收它做得对不对**。
>
> 另一份文档 `docs/必读1-开发约定.md` 是给 agent 读的（一页纸讲清所有规矩，省它瞎翻）。**你不用看它。**

---

## 0. 四个词，先认清

| 词 | 就是 | 你在哪看到它 |
|---|---|---|
| **仓库** | 整个项目的大文件夹，代码都在里面 | github.com/sit-rhg/culturalwalk-platform （在组织 **CulturalWalk** 下） |
| **任务卡（issue）** | 一张"待办事项"，写了这活干什么、做完算合格的标准 | GitHub → Issues 页 |
| **交作业（PR）** | 你把改好的东西"申请合进项目"，等人点头 | GitHub → Pull requests 页 |
| **合并（Merge）** | 点一下绿色按钮，你的作业正式进项目 | 同上，PR 页面底部 |

再加两个你一定会碰到的：

- **标签**：贴在任务卡上的小色块，用来分类。比如贴 `P2` 表示"归 P2 干"，贴 `backend` 表示"这是后台的活"。看到不用慌，它只是分类贴纸。
- **负责人（Assignee）**：任务卡右边的一栏。**把负责人设成自己 = 认领这张卡**。

## 1. 开工前，每人准备 4 件事（只做一次，约 30 分钟）

| # | 做什么 | 谁来做 |
|---|---|---|
| 1 | 装 **DSH**，能打开对话窗口 | 你自己 |
| 2 | 注册 **GitHub** 账号，把用户名发给 P1 | 你自己 |
| 3 | P1 把你的账号加进组织 **CulturalWalk**，并给仓库写权限 | P1 |
| 4 | 第一次让 agent 把仓库下载到你电脑，并登录你的 GitHub | 你在 DSH 里说一句话（见 §2） |

> 第 3 步不做，后面所有人都会被系统拒绝。**这是唯一必须 P1 动手的事。**

**怎么找到这个仓库**：点右上角头像 → **Your organizations** → 点 **CulturalWalk** → Repositories → `culturalwalk-platform`。
（个人主页的「Your repositories」只列**你自己拥有的**仓库，别人邀请你协作的不会出现在那里，这是 GitHub 的设计，不是没生效。）
如果进去提示没权限，去右上角**铃铛通知**或邮件里点一次**接受邀请**。

## 2. 第一次：让 agent 帮你把环境弄好

打开 DSH，新建一个会话，把下面这段**整段复制**发过去（把 `<你的用户名>` 换成你的 GitHub 用户名，`<你的名字拼音>` 换成你自己）：

```
你是我的开发助手。我们要一起做 CulturalWalk 项目（文化路线平台）。
请按顺序做，每做完一步告诉我结果：
1. 把 https://github.com/sit-rhg/culturalwalk-platform 克隆到我的电脑
2. 在这个目录里读 docs/必读1-开发约定.md，然后告诉我：这个项目有哪几个模块、我负责哪几张卡
3. 帮我配置 GitHub 登录（用我的账号 <你的用户名>），确保我能提交代码
4. 跑一遍环境自检（后端测试 + 前端类型检查），告诉我是否都通过
我的 GitHub 用户名是 <你的用户名>，我是 P2（或 P1/P3/P4）。
我不懂技术和命令，请用大白话告诉我每一步在干什么，需要我做什么请明确说。
```

它做完，你只需要确认三件事：**仓库下载好了、能看到模块列表、自检是绿的**。

> **之前克隆过旧地址的人**：仓库已经搬到组织账号下，旧地址会自动跳转，但本地要改一下远端地址（一行命令，agent 会做）：
> `git remote set-url origin https://github.com/sit-rhg/culturalwalk-platform.git`
> 改完 `git fetch origin`，能看到最新提交就对了。

## 3. 每天开始：先问它"今天干什么"

```
看一下我的任务卡，按依赖顺序告诉我：今天最适合先做哪一张？为什么？
用大白话讲这张卡要做出什么效果，以及做完之后我在网页上能看到什么变化。
```

它会给你一张卡号和一段人话解释。**看不懂就继续问**："这一步为什么要做"、"如果一个普通用户来用，他会看到什么"。

---

## 4. 领卡（就是"我要干这个"）

三种方式，任选：

1. **让 agent 领**（推荐）：`帮我把 ID-02 这张卡的负责人设成我。`
2. **自己在网页上点**：GitHub → Issues → 点开那张卡 → 右侧 `Assignees` → 点自己的头像。
3. **喊一声**：在群里说"我领 ID-02 了"，让 P1 帮你挂上。

> 为什么必须挂名字？四个人同时开工，不挂名字就会出现两个人做同一张卡、或者某张卡没人做。

---

## 5. 干活：怎么跟 agent 说话

**万能模板**（把卡号换掉就行）：

```
请做任务卡 ID-02（登录接口 + 登录页）。
要求：
- 先读 docs/必读1-开发约定.md 里跟这张卡相关的部分
- 按卡上的验收标准做，做完把验收标准逐条对照给我看
- 接口有变化就同步改 docs/api/openapi.yaml
- 写完跑测试和类型检查，全绿再告诉我
- 用大白话告诉我：做完了我打开网页能看见什么、怎么自己试
```

**四句会让它跑偏的话，别说：**

| 别说 | 改说 |
|---|---|
| "随便弄一下就行" | "按卡上的验收标准做" |
| "把整个项目都改一遍" | "只改 ID-02 涉及的目录" |
| "不用写测试了" | "至少写一个正向、一个反例的测试" |
| "顺便把别的也优化一下" | "先只做这张卡，别的另开卡" |

**它一口气说了一大堆你看不懂的东西时**，就说：

```
停一下。用小学生能听懂的话，告诉我：你刚才改了什么、我打开网页能看到什么变化、我要怎么验证它是对的。
```

## 6. 它说做完了，你怎么判断（不用懂代码）

问它，然后**自己动手试一遍**：

1. **能用吗**：按它说的步骤点一遍，功能真的出来了吗？
2. **错了会提示吗**：故意填错（空着不填、密码打错），页面有没有中文提示？还是白屏/英文报错？
3. **该拦的拦住了吗**：不该看见的（比如别人的草稿、管理员的按钮）真的看不见吗？
4. **中文正常吗**：有没有乱码、"undefined"、英文混杂？
5. **数据是自己的吗**：换个账号登录，能看到别人的私密内容吗？（能 = 严重 bug，立刻说）

任何一条不对，就回它：`第 2 条不对：密码输错时页面白屏了，没有提示。请修。`

## 7. 交作业（开 PR）

做完一张卡，对它说：

```
这张卡做完了，请：
1. 提交代码到新分支（不要动 main）
2. 开一个 PR，标题写「ID-02 登录」，描述里写清楚：对应 issue #12、怎么验收、改了哪些地方
3. 在 PR 描述最后加一行 Closes #12
```

> `Closes #12` 的意思是"这个作业对应第 12 号任务卡"。等作业被合并，**第 12 号卡会自动打勾关闭**，不用手工去关。

然后：**把 PR 链接发到群里**，让 P1 或另一个组员看一眼（这叫 review）。一个人看就行。

---

## 8. 合并：点那个绿色按钮

PR 页面上会出现三种情况：

| 你看到 | 意思 | 怎么办 |
|---|---|---|
| ✅ 全部绿勾 | 自动检查通过 | **可以点绿色 Merge 按钮** |
| 🟡 黄点在转 | 还在检查 | 等 1–2 分钟刷新 |
| ❌ 红叉 | 有问题（测试没过/格式不对） | **别点合并**，把红叉截图发给 agent，让它修 |

**谁来点？** 谁有空谁点，但必须：**有人 review 过 + 全绿**。红了硬点，会让所有人的项目变坏。

---

## 9. 卡住了 / 出事了

| 情况 | 怎么办 |
|---|---|
| agent 改坏了，页面打不开 | 对它说：`把刚才的改动全部撤回，回到上一次能用的状态` |
| 两个人改了同一个文件冲突了 | 对它说：`我的分支和 main 冲突了，请帮我合并，别删别人的代码` |
| 不知道该做什么 | 对它说：`看一下我的卡，哪张的前置已经完成、可以开工` |
| 完全看不懂它在说什么 | 对它说：`你说的人话我听不懂，请用打比方的方式再讲一遍，不要用技术词` |
| 怀疑做错了方向 | **先停下来问 P1**，别自己猜着往下做 |

## 10. 一天的样子（参考）

```
早上   ：问 agent 今天做什么 → 领卡 → 让它讲清楚要做出什么效果
上午   ：让它写，你隔 20 分钟看一眼进度，不懂就问
中午   ：它说做完了 → 你按 §6 五条自己点一遍
下午   ：不对就让它修；对了就开 PR、发群里、等人 review、点 Merge
收尾   ：把今天遇到的问题记一句，明天丢给 agent
```

## 11. 你的活到底是什么（说清楚，免得慌）

你不是"写代码的人"，你是**产品负责人 + 验收人**：

- 你说清楚"要什么效果"（用大白话描述你希望用户看到什么）
- 你亲手点一遍，判断"对不对、顺不顺"
- 你决定"这样行了 / 这样不行，重做"

代码质量、测试、接口规范——**那是 agent 和 P1 的事**，不用你操心。

## 附录 C · 术语对照（看到就查这里）

| 你会看到 | 人话 |
|---|---|
| issue / 任务卡 | 一张待办事项 |
| label / 标签 | 贴纸，用来分类（谁干、属于哪个模块） |
| assignee / 负责人 | 这张卡归谁 |
| branch / 分支 | 你自己的草稿副本，不影响别人 |
| PR / pull request | 交作业，申请合进项目 |
| review | 别人看一眼你的作业 |
| merge | 点绿按钮，作业正式进项目 |
| CI / 检查 | 机器人自动跑的测试，绿=过，红=没过 |
| commit | 存档一次（agent 干，你不用管） |
| conflict / 冲突 | 两个人改了同一处，需要合并 |
