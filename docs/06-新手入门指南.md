# 零基础入门指南

> 给"没写过 Web 项目、没碰过 GitHub"的组员看。读完你应该能回答三个问题：
> **这是什么东西 → 我要做什么 → 怎么才不搞坏别人的东西。**
>
> 配套阅读：`docs/04-开发环境与协作.md`（规范版，字少但要求硬）、`docs/01-模块与任务看板.md`（任务全表）。

## 0. 三句话看懂这个项目

1. **它做什么**：一个"文化行走"网站。游客输入「长沙、2 天、3 个人、1000 块、想看市井文化」，系统给出一条带文化说明、时长、花费的路线；用户也能自己创作路线投稿，审核通过后大家都能看到。
2. **它由什么组成**：一个网页前端（`apps/web`）+ 一个后端接口服务（`services/api`）+ 一个数据库（Postgres）+ 一个图片仓库（MinIO）。
3. **我们四个人怎么分工**：把整个系统切成 12 个"模块"（登录、地点、路线、规划、社区……），每人负责几个模块，按 `docs/01` 里的 **57 张任务卡**逐个做，做完一张关一张。

```
你的浏览器
   │  ① 点"登录"，输入用户名密码
   ▼
前端 apps/web（Vue 页面）           ← 只负责"长什么样、点了发什么请求"
   │  ② POST /api/v1/auth/login
   ▼
后端 services/api（FastAPI）        ← 只负责"规则对不对、数据怎么存"
   │  ③ 查 users 表、比对密码哈希
   ▼
数据库 Postgres（users / routes / places …）
   │  ④ 返回 token
   ▼
前端把 token 存起来，之后每次请求都带着它 ← 后端靠它知道"你是谁"
```

## 1. 你会面对三个界面，别搞混

| 界面 | 在哪 | 你在上面干什么 |
|---|---|---|
| **GitHub 网页** | github.com/SLP-man/culturalwalk-platform | 看任务（Issues）、提改动（Pull Request）、看自动检查是否通过（CI） |
| **VS Code + 本地文件夹** | 你电脑上的 `culturalwalk-platform/` | 真正写代码的地方 |
| **跑起来的网站** | 浏览器打开 `localhost:5173` | 验证你写的东西对不对 |

**关键认知**：GitHub 上的代码不是你电脑上的代码。你在本地改完，要"推"（push）上去别人才看得见；别人改了，你要"拉"（pull）下来才同步。这一步是新手最容易出事的地方。

## 2. 十二个名词，一次讲透

| 名词 | 一句话解释 | 类比 |
|---|---|---|
| 仓库 repository | 一个项目文件夹 + 它的全部历史 | 一个有存档功能的共享网盘文件夹 |
| 克隆 clone | 把仓库第一次下载到自己电脑 | 把网盘文件夹同步到本地 |
| 分支 branch | 从主线拉出来的一条平行时间线，你在上面随便改，不影响别人 | 写论文时另存为"论文v2-试验版.docx" |
| 提交 commit | 把一次改动打包存档，附一句说明 | 游戏存档点 |
| 推送 push | 把本地提交上传到 GitHub | 把存档同步到云端 |
| 拉取 pull | 把 GitHub 上的新提交下载到本地 | 云端存档同步回本地 |
| **Pull Request（PR）** | 「我把 `feat/xxx` 分支改好了，请把它合进 `main`」的正式申请，附带差异对比和自动检查结果 | 交作业，老师批改通过才计入成绩 |
| `main` | 主分支，**永远保持能跑**，只有通过 PR 才能进 | 正式版论文，不能随便改 |
| Issue | 一条任务工单（我们已把 57 张卡都建好了） | 待办清单里的一条，可以指派给人 |
| CI | 每次你推代码，GitHub 自动跑一遍检查（格式、测试、类型、契约、compose 语法） | 交作业前的自动查重 + 格式审查 |
| 迁移 migration | 改数据库表结构的"脚本版操作记录"（加字段、建表） | 给数据库结构拍快照的 git |
| 模块 module | 后端按业务切的一个文件夹，比如 `identity/`（登录）、`routes/`（路线） | 一个部门，各管一摊，不许越界插手 |

## 3. 第一次跑起来（照着抄，20 分钟）

### 3.1 装依赖（只做一次）

| 软件 | 版本 | 干嘛用的 |
|---|---|---|
| Docker Desktop | 任意较新版 | 一键起数据库和图片仓库，不用自己装 Postgres |
| Python | 3.12 | 跑后端 |
| Node.js | 20（装完自带 `npm`） | 跑前端 |
| pnpm | `npm i -g pnpm` | 前端包管理器（比 npm 快，项目用它） |
| Git | 任意 | 版本管理 |
| VS Code | 任意 | 写代码（建议装插件：Python、Vue - Official、Even Better TOML） |

### 3.2 拿到代码

```bash
git clone https://github.com/SLP-man/culturalwalk-platform.git
cd culturalwalk-platform
```

> 如果你看到的是 `fatal: could not read Username`：说明 GitHub 要你登录。用 VS Code 打开后它会弹登录框，点 Allow 走浏览器授权即可（或让 P1 给你发邀请后，用 `git config --global user.name "你的名字"` 配好身份）。

### 3.3 起数据库

```bash
cd infra
cp .env.example .env      # Windows PowerShell: copy .env.example .env
docker compose up -d db minio
docker compose ps         # 两个都 healthy 才算好
cd ..
```

**成功的样子**：`docker compose ps` 里 `db` 和 `minio` 的状态是 `running (healthy)`。
**踩坑**：Docker Desktop 没启动会报 `Cannot connect to the Docker daemon`——先打开 Docker Desktop 等它转完。

### 3.4 起后端

```bash
cd services/api
python -m venv .venv
# Windows: .venv\Scripts\activate     macOS/Linux: source .venv/bin/activate
pip install -e ".[dev]"                # 国内慢就加：-i https://pypi.tuna.tsinghua.edu.cn/simple
alembic upgrade head                   # 建表
uvicorn app.main:app --reload          # 起服务
```

**成功的样子**：终端显示 `Uvicorn running on http://127.0.0.1:8000`，浏览器打开 <http://localhost:8000/docs> 能看到一排接口分组。
**踩坑**：
- `alembic: command not found` → 虚拟环境没激活，回到上一步；
- 连不上数据库 → 3.3 没起好，或 `.env` 里 `DATABASE_URL` 不对；
- 端口被占 → `uvicorn app.main:app --reload --port 8001`。

### 3.5 起前端（**另开一个终端**）

```bash
pnpm install        # 在仓库根目录跑（这是 pnpm 工作区，锁文件在根）
pnpm dev
```

**成功的样子**：浏览器打开 <http://localhost:5173>，能看到首页和顶部导航。
**踩坑**：`pnpm: command not found` → 没装 pnpm；`EACCES` 权限报错 → 别用 sudo，改用 `npm i -g pnpm --prefix ~/.local`。

### 3.6 本地自检三件套（交 PR 前必跑）

```bash
pnpm typecheck                       # 前端类型
pnpm -C services/api lint            # 后端格式/风格（等价 ruff check + format --check）
pnpm -C services/api test            # 后端单元测试
python scripts/check_contract.py     # 契约引用完整性
```

> 记不住就跑 `pnpm verify`（四个一起跑）。

四行全绿 → 你本地就是"能过 CI"的状态，可以提 PR 了。

## 4. 认领一张卡

打开 <https://github.com/SLP-man/culturalwalk-platform/issues>，你会看到 51 条开着的任务（6 条 M0 已完成关闭）。

### 4.1 怎么筛出"我的"

```
label:identity          # 只我自己模块的（把 identity 换成你的模块：catalog / routes / planner / community / media …）
label:M1                # 只看第一阶段
label:P2                # 只看 P2 角色的卡
no:assignee             # 只看看还没人领的
```

### 4.2 卡上的信息怎么读

以 `#7 [ID-01] 用户与会话表` 为例：

| 卡里的字段 | 意思是 |
|---|---|
| **输出**：`modules/identity/models.py + 迁移` | 你最后要交的文件，就这些，别多改别的 |
| **验收**：`alembic upgrade head 建表成功` | 怎么算做完——照着这句自己跑一遍 |
| **依赖**：`无` | 有依赖的卡，等上游合并了再开始（不然你写的接口没数据） |
| **估计**：1 人天 | 大概一天，超过两天做不完就该在 issue 里说 |
| **负责角色**：P2 | 建议谁做（不强制，但别抢别人的主责模块） |

### 4.3 认领动作

在 issue 右侧 **Assignees** → `assign yourself`。这就够了，不用在群里喊。
**规则**：一张卡只给一个人；认领后 24 小时没开 PR，卡会被收回重分配（`tasks/README.md` 第 4 节）。

## 5. 干活的九步流水线

> 记住一句话：**永远不在 `main` 上直接写代码。**

```bash
# ① 同步主线（每次开工前都做）
git switch main
git pull

# ② 建自己的分支：feat/<模块>-<卡号>
git switch -c feat/identity-ID-01

# ③ 写代码（只改这张卡"输出"里列的文件）
#    ...

# ④ 本地自检
pnpm verify

# ⑤ 提交（一条改动一个 commit，说明写"做了什么"，不是"改了文件"）
git add -A
git commit -m "feat(identity): 建 users 表与首个迁移"

# ⑥ 推送
git push -u origin feat/identity-ID-01

# ⑦ 网页上开 PR（推完终端会给你一条链接，点它）
```

**PR 标题**：`feat(identity): 建 users 表与首个迁移`
**PR 正文**（直接抄这个模板）：

```markdown
## 这张卡做了什么
- 建 `users` 表：id / username / password_hash / role / bio / created_at
- 新增迁移 `0002_users.py`

## 怎么验证的
- [x] `alembic upgrade head` 成功，`\d users` 能看到 7 个字段
- [x] `alembic downgrade base` 再 `upgrade head` 可重放
- [x] `pnpm -C services/api test` 18 passed

## 注意
- 只动了 `services/api/app/modules/identity/` 和 `migrations/`

Closes #7
```

> **`Closes #7` 是关键**：PR 合并后，那条 issue 会自动关闭，看板自动推进。不写就得手工关。

**⑧ 等 CI**：PR 页面下方会出现 `backend / frontend / contract / compose` 四个检查。全绿才轮到人看。
**⑨ 找人 review**：把 PR 链接发给任意一个组员（`main` 分支保护要求至少 1 人 approve）。他点 **Approve** → 你点 **Merge pull request**（选 **Squash**）→ 分支自动删掉。

## 6. 「我正在写的这行代码，在整个系统里是哪块」

这是新手最容易迷路的地方。拿 `ID-02 注册/登录/退出` 走一遍，从上到下：

### 第 1 层：用户看到什么

用户在 `localhost:5173` 的登录页输入 `xiaoming / 123456`，点"登录"。
前端 `apps/web/src/pages/LoginPage.vue` 调 `apiClient.post('/auth/login', {...})`。

### 第 2 层：请求长什么样（契约层，先定死）

`docs/api/openapi.yaml` 里已经写好了：

```yaml
POST /api/v1/auth/login
  请求: { "username": "xiaoming", "password": "123456" }
  200:  { "access_token": "...", "token_type": "bearer" }
  401:  { "error": { "code": "INVALID_CREDENTIALS", "message": "用户名或密码错误" } }
```

**契约先行**的意思是：先有这个文件，前端后端各自照着它写，谁也不用等谁。

### 第 3 层：你要写的三个文件（分层，不许穿透）

```
services/api/app/modules/identity/
├── models.py     ← 表长什么样：users(id, username, password_hash, role, bio, created_at)
├── schemas.py    ← 进出长什么样：LoginIn{username,password} / TokenOut{access_token}
├── repository.py ← 只碰 SQL：get_by_username() / create()
├── service.py    ← 只写规则：密码对不对、hash 怎么算、token 怎么签、登录失败记什么
└── router.py     ← 只做翻译：HTTP 请求 → 调 service → HTTP 响应
```

**规矩（`AGENTS.md` 硬要求）**：

| 层 | 能做 | 不能做 |
|---|---|---|
| `router.py` | 解析参数、返回状态码 | 写 `select(`、写业务判断、直接改数据库 |
| `service.py` | 全部业务规则、状态流转 | 直接拼 SQL 字符串 |
| `repository.py` | SQL 查询 | 业务判断（比如"密码对不对"不能写这） |

写错了会被 review 打回：`router` 里出现 `select(` 就是典型错误。

### 第 4 层：别人怎么用你写的东西

做完之后，别的模块只要一行就能拿到"当前是谁"：

```python
from app.modules.identity.deps import get_current_user

@router.post("/route-drafts")
def create_draft(payload: DraftIn, user=Depends(get_current_user)):
    ...  # 这里 user.id 就是作者
```

管理端要判权限：

```python
@router.post("/admin/publish", dependencies=[Depends(require_role("admin"))])
```

**这就是为什么 ID-01~04 要最先做**：后面 40 多张卡的验收条件里都写着"登录用户……"。

### 第 5 层：怎么证明你做对了

```bash
curl -X POST localhost:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"xiaoming","password":"123456"}'
# 期望：200 + {"access_token":"..."}

curl -X POST localhost:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"xiaoming","password":"wrong"}'
# 期望：401 + INVALID_CREDENTIALS   ← 这条是"负例"，必须测
```

## 7. 十条防错清单（照着做，基本不会出事）

1. **不直推 `main`**。分支保护会拦你；就算你是 owner 能推，也别推。
2. **只改自己卡里"输出"列的文件**。改到别人模块 = 冲突制造机。
3. **不手改生成文件**：`packages/contracts/src/types.ts`、`tasks/*`、`docs/01-*`。要改就改源头再跑脚本。
4. **不提交 `.env`、密码、token**。`.gitignore` 已经挡住了，但别自己 `git add -f`。
5. **迁移只加不删**：新迁移文件用 `alembic revision -m "..."` 生成，别去改已经推上去的旧迁移。
6. **业务规则写 `service`，不写 `router`**（见第 6 节表格）。
7. **交 PR 前跑 `pnpm verify`**，别让 CI 替你发现格式问题。
8. **一个 PR 只做一张卡**。顺手改三个不相干的东西，review 会拖到下周。
9. **PR 正文写 `Closes #编号`**，否则 issue 不会自动关。
10. **每天开工先 `git switch main && git pull`**，别在三天前的代码上继续写。

## 8. 常见报错速查

| 报错 | 原因 | 怎么办 |
|---|---|---|
| `pnpm: command not found` | 没装 pnpm | `npm i -g pnpm` |
| `Cannot connect to the Docker daemon` | Docker 没启动 | 打开 Docker Desktop 等绿 |
| `connection refused ... 5432` | 数据库没起 | `docker compose up -d db` |
| `alembic: command not found` | venv 没激活 | `.venv\Scripts\activate` |
| `Multiple head revisions are present` | 两个人各加了一个迁移 | 让 P1 用 `alembic merge -m "merge"` 合并 |
| `401 Unauthorized` | 没登录 / token 过期 | 重新登录拿 token |
| `403 Forbidden` | 角色不够（比如普通用户点发布） | 这是**正确行为**，别改代码 |
| `422 Unprocessable Entity` | 请求体字段不对 | 对照 `openapi.yaml` 看必填字段 |
| PR 显示 `This branch has conflicts` | 你和别人改了同一行 | 本地 `git switch main && git pull`，再 `git switch 你的分支 && git merge main`，手改冲突后提交 |
| PR 显示 `This branch is out-of-date` | 别人先合了 | `git merge main` 后推送即可 |
| CI `contract` 红 | 改了 `openapi.yaml` 但 `$ref` 指向不存在的东西 | 本地跑 `python scripts/check_contract.py` 看具体路径 |
| CI `backend` 红在 `ruff format --check` | 格式不对 | 本地 `ruff format .` 再提交 |
| `git push` 提示 `Updates were rejected` | 远端有你没有的提交 | 先 `git pull --rebase` 再 push |
| 终端中文乱码（Windows） | 编码不是 UTF-8 | 命令前加 `chcp 65001`，或改用 PowerShell |

## 10. 卡住了怎么问（照着填，别只说"跑不起来"）

```
我在做：#12 [RS-03] 路线草稿提交
我已经做了：建了分支、写了 submit()、本地 test 通过
期望：POST /route-drafts/12/submit 返回 200 和 status=SUBMITTED
实际：返回 500，日志是 KeyError: 'cultural_note'
我试过：把 cultural_note 改成 note 就好了，但契约里字段名是 cultural_note，不敢乱改
```

**好问题的三要素**：我在做什么 → 期望什么 → 实际是什么（附报错原文）。有这三条，别人 30 秒就能帮你。

## 附：这个项目里"绝对不能碰"的东西

| 东西 | 为什么 |
|---|---|
| `main` 分支直接改 | 保护规则会拦；绕过会搞坏所有人的基线 |
| `packages/contracts/src/types.ts` | 自动生成，手改会被下次生成覆盖，且 CI 会红 |
| `tasks/*`、`docs/01-*` | 同样自动生成，真源是看板表格 |
| 别人的模块目录 | 冲突 + 责任不清 |
| `.env` / 任何 token | 泄露后所有人要换密钥 |
| 已经推送的迁移文件 | 别人可能已经跑过，改了就永久不一致 |
