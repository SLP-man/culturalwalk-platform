# CulturalWalk 新手开发手册：从不会 AI 开发到完成第一条纵向链路

> **手册版本**：v0.1
>
> **适用对象**：刚开始学习软件开发、准备使用 AI 辅助编程的成员。
>
> **配套规范**：`设计文档/CulturalWalk_VibeCoding底层架构与开发范式.md`
>
> **重要说明**：这是一份“解释和实践手册”，不是已经完成的 CulturalWalk 源代码，也不代表地图、AI、云服务或备案已经开通。真正开发时，必须以项目仓库中的 OpenAPI、ADR、测试和当前任务说明为准。

---

## 0. 先给新手的结论

如果你只记住下面十句话，就已经掌握了这套开发规范的核心：

1. **先做一个能运行的最小产品，不要先做“大而全”的平台。**
2. **先把规则写清楚，再让 AI 生成代码。**
3. **AI 是助手，不是产品负责人、审核员或上线审批人。**
4. **路线、投稿、审核、发布是不同概念，不能共用一个模糊的 `status`。**
5. **已提交、已审核的版本要冻结；要修改时复制成新的编辑副本。**
6. **接口契约先于前后端实现，`docs/api/openapi.yaml` 是 HTTP API 的唯一事实源。**
7. **后端才是安全边界；前端隐藏按钮不等于权限控制。**
8. **地图和 AI 都是外部供应商，必须通过 Adapter 隔离，不能把供应商细节散落到业务代码里。**
9. **每次让 AI 改代码，都要限定范围、给出验收命令，并由人检查结果。**
10. **“代码能跑”不等于“功能完成”；完成必须有测试、权限、审计和回滚证据。**

## 2. 我们到底要做什么

### 2.1 一句话说明

CulturalWalk 是一个让用户发现、创建、提交和共同完善**城市文化路线**的平台。

一条路线不只是地图上的几条线，而是由以下内容组成：

- 路线标题和主题；
- 按顺序排列的文化节点；
- 每个节点的地址、坐标、图片和文化说明；
- 内容来源和作者；
- 适合的人群、时长、交通方式等说明；
- 审核记录和发布版本。

### 2.2 MVP 要完成的真实闭环

首期不是做所有智能功能，而是完成下面这条链路：

```text
匿名用户浏览公开路线
        ↓
查看路线详情和文化节点
        ↓
登录用户创建路线草稿
        ↓
填写来源、节点和媒体授权信息
        ↓
提交固定版本
        ↓
审核员领取并审核
        ↓
退回修改 / 拒绝 / 通过
        ↓
编辑者发布已通过的固定版本
        ↓
匿名用户再次浏览
        ↓
必要时下线并留下审计记录
```

这条链路叫**纵向切片（vertical slice）**：它从用户界面一直贯穿到 API、数据库、审核和发布，而不是只把某一层做得很漂亮。

### 2.3 首期明确不做什么

以下事项不是首期 MVP 的验收条件：

- 原生 iOS/Android App；
- 同时开发 H5、小程序和原生 App；
- 自建道路级最短路径算法；
- 完整离线地图包；
- 数字人、复杂 NPC、多模型自动选择；
- 多城市大规模运营；
- 微服务、Kubernetes、事件总线；
- AI 自动审核后直接发布；
- 没有真实用户验证就建设复杂推荐系统。

**为什么要写“不做什么”**：新手使用 AI 时很容易把“以后可能做”误认为“现在必须做”。非目标是保护时间和系统复杂度。

## 3. 读懂规范中的三种标记

原规范使用三个级别：

### 3.1 MUST：现在不做就不能算完成

例子：

- AI 生成内容不能直接发布；
- 后端必须执行 RBAC 权限检查；
- 公开接口只能读取 `PUBLISHED` 版本；
- 密钥不能进入浏览器代码；
- 数据库迁移必须可重放；
- 高风险动作必须有审计记录。

MUST 是验收条件，不是“建议”。如果一个 AI 任务声称完成，但违反 MUST，应该退回修改。

### 3.2 SHOULD：当前推荐，但要用证据确认

例子：

- Vue 3 + TypeScript + Vite；
- FastAPI + Pydantic + SQLAlchemy/Alembic；
- 使用轻量异步任务；
- 使用 Docker Compose 或云厂商部署模板。

SHOULD 不是绝对命令。团队应通过 ADR、技能调查、小型垂直切片和维护成本比较后冻结。当前规范中，前端框架由 ADR-0011、后端框架由 ADR-0012 决定。

### 3.3 LATER：未来再做，不得偷偷进入 MVP

例子：

- 离线地图；
- 向量检索和复杂推荐；
- 多地域部署；
- Kubernetes；
- 复杂 CQRS 或事件溯源。

LATER 不是“永远不做”，而是要等真实用户、容量、成本或合规证据出现后再做。

### 3.4 事实、假设、待验证

| 标记 | 含义 | 例子 |
|---|---|---|
| 事实 | 已经有会议、代码审计或明确文件证据 | H5 首发、AI 必须人工确认 |
| 假设 | 当前为了推进设计而采用的推测 | 试点流量较小、8 人团队可以按模块协作 |
| 待验证 | 不验证不能上线的事项 | 地图商用授权、云价格、备案、AI 数据保留 |

新手最容易犯的错误是把“看起来合理”当成事实。例如“某地图 SDK 开源，所以地图数据可以商用”就是错误推论。代码许可证和地图瓦片、POI、导航数据许可证是不同问题。

## 4. 先学会看一张架构图

系统可以先粗略理解为五层：

```text
用户 H5 / 管理端
        ↓ HTTPS
反向代理：TLS、限流、请求大小限制
        ↓
模块化单体 API：身份、路线、投稿、审核、发布、地图、AI、媒体
        ↓
PostgreSQL：用户、路线版本、投稿、审核和审计事实
对象存储：图片和附件
轻量异步任务：AI 草稿、缩略图、通知
        ↓
外部 Provider：地图 / 导航 / AI
```

### 4.1 每个组件用大白话解释

| 组件 | 大白话解释 | 初学者要记住 |
|---|---|---|
| H5 | 手机浏览器里的网页 | 负责展示和收集输入，不负责最终授权 |
| 管理端 | 给审核员和编辑者使用的页面 | 不能直接改数据库绕过状态机 |
| API | 前端和后端说话的入口 | 先看契约和权限，再写实现 |
| 模块化单体 | 一个部署应用，内部按业务模块隔离 | 不是“所有代码乱放在一起” |
| PostgreSQL | 记录业务事实的数据库 | 交易、版本、审核要可追溯 |
| 对象存储 | 专门存图片和文件的地方 | 大文件不要直接塞数据库 |
| 异步任务 | 稍后执行且可重试的工作 | AI 完成任务不等于可以发布 |
| Provider | 外部地图或 AI 服务 | 外部返回值不可信，必须校验 |
| Adapter | 把外部服务翻译成内部统一接口 | 未来换供应商时少改业务代码 |
| 审计 | 谁在何时对什么做了什么 | 高风险动作必须能追责 |

### 4.2 一次请求是怎样流转的

以“匿名查看已发布路线”为例：

1. 手机浏览器发送 `GET /api/v1/routes/route-123`。
2. 反向代理检查 HTTPS、请求大小和基础限流。
3. API 的 `publication` 模块处理请求。
4. 服务只查询当前 `PUBLISHED` publication 指向的固定版本。
5. 数据库返回路线和节点。
6. API 组装公开 DTO，不返回草稿、审核意见、私有手机号或内部密钥。
7. H5 把结果渲染为路线详情页面。

以“提交路线”为例，API 需要额外做：

- 检查当前用户是否为草稿 owner；
- 检查草稿是否仍是 `EDITING`；
- 检查来源和媒体授权；
- 生成不可变快照和 hash；
- 创建投稿和审核任务；
- 写审计事件；
- 任一步失败，整个事务回滚。

## 5. 为什么选择模块化单体，而不是微服务

### 5.1 三个容易混淆的概念

- **单体应用**：部署成一个应用。
- **模块化单体**：部署仍是一个应用，但内部有清晰的业务模块和依赖边界。
- **微服务**：多个独立进程或服务，分别部署、通信和运维。

模块化单体不是“简单项目”，而是**先把边界设计好，但暂时不为独立部署付费**。

### 5.2 方案对比

| 方案 | 优点 | 代价 | 适合 CulturalWalk 吗 |
|---|---|---|---|
| 一个脚本/无结构项目 | 上手最快 | 代码互相调用，权限和状态很快失控 | 只适合一次性 Demo，不适合 MVP |
| 普通分层单体 | 比脚本清晰 | 业务边界可能被 `utils` 和共享模型冲垮 | 可过渡，但要加强模块约束 |
| **模块化单体** | 一次部署、事务简单、模块边界清晰 | 需要团队遵守依赖规则 | **当前首选** |
| 微服务 | 独立扩展和隔离故障 | 多部署、多网络、多监控、分布式一致性 | 当前团队和流量没有必要 |
| Kubernetes + 微服务 | 大规模平台能力强 | 运维、成本和学习曲线很高 | 当前明显过度设计 |

### 5.3 选择模块化单体的原因

CulturalWalk 的核心一致性链路是：

```text
投稿快照 → 审核结论 → 发布固定版本
```

这条链路需要事务、版本匹配和审计。8 人团队、单城市低成本公网试点，不值得为每个模块增加网络调用、部署、监控和故障排查成本。

所以规范选择：

- 一个部署单元；
- `identity`、`routes`、`submissions`、`publication` 等模块各自拥有业务规则；
- 跨模块只调用公开应用服务或端口；
- 数据库迁移集中审查；
- 等有容量或故障隔离证据后，再考虑拆服务。

### 5.4 什么时候才考虑微服务

不要因为“公司都在用微服务”就拆分。至少需要出现可测量证据，例如：

- 某模块必须独立扩容；
- 某模块的故障必须与主应用隔离；
- 团队规模足以承担多服务运维；
- 单体发布频率或构建时间成为瓶颈；
- 合规要求不同模块隔离部署。

在证据出现前，模块化单体更容易理解、测试和回滚。

## 6. 为什么选择 PostgreSQL、对象存储和轻量异步任务

### 6.1 PostgreSQL：因为我们要保存“事实”和“历史”

路线平台不是只有一个不断覆盖的 JSON。我们需要知道：

- 谁创建了路线；
- 哪个版本在什么时候提交；
- 审核员看到了哪个固定快照；
- 谁批准了哪个 hash；
- 哪个版本当前公开；
- 某张图片是否扫描通过和获得授权。

这些需求需要事务、外键、条件更新、版本和查询能力，所以 PostgreSQL 作为业务事实源更合适。

### 6.2 为什么不是一开始用 MongoDB 或把 JSON 文件放磁盘

| 方案 | 适合场景 | 当前问题 |
|---|---|---|
| JSON 文件 | 单机演示、临时 fixture | 并发、权限、审计、回滚和多用户很快变复杂 |
| MongoDB | 结构变化快、文档型数据 | 仍要自行设计审核事务、引用关系和一致性 |
| Redis | 缓存、短期状态、队列辅助 | 不适合作为完整审核事实源 |
| PostgreSQL | 事务、版本、关系、审计、迁移 | 需要学习 SQL 和迁移，但长期更稳妥 |

并不是说其他数据库永远不能用，而是当前业务的主要难题是**一致性和可追溯**，不是海量无结构文档。

### 6.3 为什么图片不放 PostgreSQL

数据库保存图片的元数据，例如：

- `media_asset_id`；
- 对象 key；
- 文件类型和大小；
- checksum；
- 扫描状态；
- 授权声明。

原图、缩略图等大对象放对象存储。这样数据库更容易备份、查询和迁移。

### 6.4 为什么 AI、缩略图使用异步任务

AI 生成和图片处理可能慢、失败或需要重试。同步请求一直等着会导致：

- 页面超时；
- 用户重复点击；
- 费用重复；
- 失败难以追踪。

因此 API 返回 `202 Accepted` 和 `run_id`，后台任务再执行：

```text
QUEUED → RUNNING → SUCCEEDED
                    ↘ FAILED / TIMED_OUT / REJECTED_POLICY
```

异步任务只产生候选或处理结果，不能直接调用 `approve`、`publish`、`unpublish`。

## 7. 为什么必须 API-first：先契约，再写代码

### 7.1 API 是前后端之间的“合同”

如果前端认为字段叫 `routeTitle`，后端返回 `title`，两边都可能“自己看着写完”，最后却无法联调。

API-first 的顺序是：

```text
需求 → OpenAPI 契约 → 生成客户端类型 → 前端/后端并行实现 → 契约测试
```

规范指定 `docs/api/openapi.yaml` 为唯一 HTTP 契约源，因为：

- 前端知道请求、响应和错误长什么样；
- 后端知道输入校验和状态码；
- 可以生成 TypeScript 类型；
- 可以做破坏性变更检查；
- 8 人并行时减少口头约定。

### 7.2 数据库模型不是公共 API

数据库字段是内部实现，不应直接暴露 ORM 模型。原因是：

- 数据库可能有内部字段；
- 表结构变更不应该自动破坏客户端；
- 权限和脱敏需要在 API 层明确处理；
- 公共接口只应返回当前允许看到的内容。

因此，后端应组装 DTO（数据传输对象），而不是把整张表直接序列化。

### 7.3 一个简单的错误响应

所有 API 错误使用统一外形：

```json
{
  "error": {
    "code": "ROUTE_VERSION_CONFLICT",
    "message": "路线版本已发生变化，请刷新后重试",
    "request_id": "req_01J...",
    "details": []
  }
}
```

对外不要返回：

- Python/JavaScript 堆栈；
- SQL；
- API key；
- 供应商原始错误；
- 其他用户的隐私。

### 7.4 新手实现一个 API 的步骤

以“创建路线草稿”为例：

1. 找到 OpenAPI 中的 `POST /api/v1/route-drafts`。
2. 读清楚登录要求、请求字段、响应字段和错误码。
3. 确认 owner 必须是当前登录用户。
4. 先写一个失败测试：匿名请求应返回 401。
5. 再写正常测试：登录用户创建后只能看到自己的草稿。
6. 实现后端应用服务，不让路由处理函数塞满业务规则。
7. 生成或更新前端 API client。
8. 运行单元、合约和集成测试。
9. 在 PR 中报告改动路径、命令、结果和未验证项。

### 7.5 为什么需要幂等键和 `If-Match`

**幂等键（Idempotency-Key）**解决“用户点击一次但网络重试两次”的问题。投稿、发布、上传确认等写操作重复提交时，服务应返回原结果，而不是创建两个投稿。

**`If-Match` / `lock_version`**解决“两个页面同时编辑覆盖彼此”的问题。版本不一致时返回 409，让用户刷新，而不是静默覆盖。

## 8. 为什么要用四套状态机，而不是一个 `status`

### 8.1 四个对象分别回答不同问题

| 对象 | 它回答的问题 | 示例状态 |
|---|---|---|
| `route_drafts` | 作者当前能不能继续编辑？ | `EDITING`、`SUBMITTED_LOCKED` |
| `submissions` | 这一次投稿审核结果是什么？ | `PENDING_REVIEW`、`APPROVED` |
| `review_tasks` | 审核工作有没有被领取和完成？ | `OPEN`、`CLAIMED` |
| `publications` | 哪个版本现在对公众可见？ | `PUBLISHED`、`UNPUBLISHED` |

如果只使用一个 `status`，很快会遇到矛盾：

- 路线审核通过了，但还没有正式发布；
- 审核任务已完成，但路线下线了；
- 作者正在修改新副本，但旧版本仍在公开；
- 投稿被拒绝后重新编辑，但旧投稿记录仍要保留。

### 8.2 为什么已提交版本不能原地修改

审核员批准的是某个具体内容。如果作者随后直接修改同一个对象，批准就失去了意义。

正确做法：

```text
旧固定版本（只读）
        ↓ fork
新的 EDITING 草稿
        ↓ resubmit
新的固定版本 + 新投稿
```

这样可以明确回答：“审核员批准的到底是哪一版？”

### 8.3 常见状态流转

投稿状态示例：

```text
PENDING_REVIEW
   ├── approve → APPROVED
   ├── request-changes → CHANGES_REQUESTED → SUPERSEDED（重新投稿）
   ├── reject → REJECTED → REOPENED（编辑者批准重开）→ SUPERSEDED
   └── withdraw → WITHDRAWN
```

注意：`REOPENED` 只表示“允许重新编辑”，不表示“内容已审核通过”。重新提交后，必须再次进入 `PENDING_REVIEW`。

### 8.4 发布的硬规则

公共列表和详情只能查询：

- 当前 publication pointer 指向的版本；
- `publications.state = PUBLISHED`；
- 通过审核并匹配精确 `route_version_id + content_hash` 的内容。

不能因为客户端传了 `?status=draft` 就把草稿返回给匿名用户。未知路线和未发布路线应返回同形 404，避免泄露“这个 ID 可能存在”。

## 9. 权限：为什么后端检查比前端按钮更重要

### 9.1 角色的基本含义

| 角色 | 可以做什么 | 不能做什么 |
|---|---|---|
| `visitor` | 浏览公开路线 | 创建草稿、调用管理 API |
| `contributor` | 创建自己的草稿、投稿、查看自己的意见 | 审核或发布自己的路线 |
| `reviewer` | 领取审核任务、退回、拒绝、通过 | 审核自己的投稿 |
| `editor` | 管理内容、发布、下线、处理申诉 | 不必要地查看私人信息 |
| `admin` | 账号、角色、策略、紧急下线 | 不应成为所有操作都无审计的万能账号 |
| `ops` | 健康、指标、受限任务重试 | 不能修改审核结论或查看正文隐私 |
| `audit-reader` | 查询和脱敏导出审计 | 不能写业务对象或修改审计 |
| `system` | 执行明确授权的后台任务 | 不能审批、发布或下线 |

### 9.2 每次请求的授权顺序

后端要依次检查：

1. 请求有没有认证主体？
2. 这个主体有没有所需角色或 scope？
3. 对象是不是这个用户自己的？
4. 任务是不是分配给这个审核员？
5. 当前状态允许这个动作吗？
6. 版本、hash 和并发条件是否匹配？
7. 是否需要记录审计？

### 9.3 新手必须写的权限负例

不要只测“正常用户能成功”，还要测试：

- 匿名用户创建草稿失败；
- 用户不能读取他人的投稿；
- 投稿作者不能领取或通过自己的审核任务；
- 未领取任务的 reviewer 不能作决定；
- `ops` 不能调用发布接口；
- `system` 不能调用 approve/publish/unpublish；
- 匿名用户不能读取草稿、隔离媒体和审核意见。

**负例测试不是额外工作，而是权限功能本身的一部分。**

## 10. 地图规范：地图代码、地图数据和导航不是一回事

### 10.1 地图能力分三层

界面上要区分：

1. **点位展示**：在地图上标出文化节点。
2. **访问顺序连线**：表示先去 A，再去 B；不代表道路最短路径。
3. **供应商路线预览或外部导航跳转**：只有在 Provider 能力和许可确认后才能使用。

没有道路 API 证据时，不要把连线写成“最短路线”“实时导航”或“精确步行时间”。

### 10.2 为什么需要 `MapProvider` Adapter

业务模块只依赖内部接口，例如：

```text
geocode(query, region) -> PlaceCandidate[]
reverse_geocode(lat, lon) -> Address
route_preview(points, mode) -> RoutePreview
navigation_link(points, mode) -> SafeExternalLink
```

具体供应商放在 Adapter 里。这样：

- 供应商变更时少改业务代码；
- 统一超时和错误码；
- 可以使用 fake provider 做测试；
- 供应商配额、价格和合规问题不会扩散到所有模块。

### 10.3 坐标新手注意事项

规范暂定内部 canonical 坐标为 WGS84 / `OGC:CRS84`，但具体供应商坐标系必须核验。

要记住：

- `lat` 是纬度，`lon` 是经度；
- GeoJSON 数组是 `[longitude, latitude]`，不是 `[latitude, longitude]`；
- GCJ-02、BD-09 等偏移坐标不能冒充 WGS84；
- 前端页面不要到处复制坐标转换公式；
- 坐标转换只放在 Provider Adapter，并用已知控制点测试。

代码库开源不等于瓦片、POI、字体或导航数据可以自由商用。接入前要有供应商文档、合同和法务结论。

## 11. AI 规范：AI 只生成候选，不拥有发布权

### 11.1 AI 可以做什么

首期可以让 AI 辅助：

- 根据已有节点生成路线草稿；
- 整理文化介绍的候选文本；
- 提示缺少来源的字段；
- 生成编辑建议；
- 帮开发者写测试、样板代码和文档。

### 11.2 AI 不能做什么

AI 不得：

- 把未经确认的历史信息直接当事实；
- 直接写入公开发布表；
- 调用 `approve`、`publish`、`unpublish`；
- 绕过作者确认和审核员审核；
- 在 prompt 中接收不必要的手机号、证件、私人地址或审核隐私；
- 因为输出“看起来很合理”就被当成来源。

### 11.3 AI 内容的正确流程

```text
用户/作者输入
      ↓
AI generation run（保存 provider、model、prompt 版本、input hash）
      ↓
结构化校验和安全检查
      ↓
字段级候选：ACCEPT / EDIT / REJECT
      ↓
作者确认并形成新的草稿版本
      ↓
人工 reviewer 审核来源和内容
      ↓
editor 发布精确批准版本
```

作者确认不等于 reviewer 审核，reviewer 审核也不等于 editor 发布。三个动作都要可追踪。

### 11.4 为什么使用异步 `run_id`

AI 调用可能慢、超时、被限流或重复回调。每次调用应该有独立 `run_id` 和状态：

- `QUEUED`；
- `RUNNING`；
- `SUCCEEDED`；
- `FAILED`；
- `TIMED_OUT`；
- `REJECTED_POLICY`；
- `CANCEL_REQUESTED`；
- `CANCELLED`。

重试要新建 run，并通过 `parent_run_id` 关联，不能无限自动重试。

### 11.5 字段级采纳为什么重要

不要把整段 AI 输出一键复制到路线。应记录：

- JSON path，例如 `summary`；
- suggestion hash；
- `ACCEPT`、`EDIT` 或 `REJECT`；
- 操作者和时间；
- 修改前后摘要 hash；
- run_id 和 prompt 版本。

这样将来出现错误时，能找到哪一次生成、哪一个人、哪个字段进入了版本。

## 12. 媒体上传：为什么不能“收到图片就直接展示”

用户上传图片可能包含：

- 恶意脚本或畸形文件；
- 伪造 MIME 类型；
- EXIF/GPS 精确位置；
- 未授权的版权内容；
- 超大文件和资源消耗攻击。

推荐流程：

```text
创建 upload intent
      ↓
浏览器使用短期签名 URL 直传隔离区
      ↓
confirm：检查 object key、大小、checksum、类型
      ↓
扫描、解码、重编码、清理 EXIF、检查授权
      ↓
CLEAN 派生对象
      ↓
固定路线版本引用 clean asset
      ↓
审核和发布
```

在 `CLEAN` 之前：

- 不能公开访问；
- 不能进入发布版本；
- 失败要留在隔离区或进入拒绝状态；
- 不能让服务器抓取用户任意 URL，避免 SSRF。

## 13. 前端和后端技术选择：为什么是“推荐”而不是“绝对命令”

### 13.1 前端：Vue 3 + TypeScript + Vite

当前规范将它列为 SHOULD，理由是：

- Vue 单文件组件容易按业务功能组织；
- TypeScript 能让接口字段更早暴露错误；
- Vite 启动和构建流程相对直接；
- 对刚开始协作的团队比较容易形成统一约定。

对比：

| 方案 | 优点 | 需要注意 |
|---|---|---|
| Vue 3 + TS + Vite | 渐进式、组件边界直观、上手平滑 | 团队仍需统一状态管理和目录约定 |
| React + Vite | 生态大、招聘和资料多 | 选择多，路由、状态、表单等约定需要主动统一 |
| Svelte | 样板代码少、体验轻 | 团队经验和生态适配要先确认 |
| 原生 HTML/JS | 最少依赖、适合极小 Demo | 复杂表单、权限界面和多人协作容易失控 |

选择方法不是争论“哪个框架最好”，而是完成一个真实小切片并比较：

- 团队是否会用；
- 移动端可访问性；
- API 类型接入；
- 构建和测试难度；
- 依赖维护成本。

这就是 ADR-0011 要记录的证据。

### 13.2 后端：FastAPI + Pydantic + SQLAlchemy/Alembic

当前规范将它列为 SHOULD，理由是：

- OpenAPI 和输入输出 schema 容易显式化；
- Pydantic 适合请求校验；
- SQLAlchemy/Alembic 可以配合数据库迁移；
- 对 API-first 和模块化单体比较自然。

对比：

| 方案 | 优点 | 代价 |
|---|---|---|
| FastAPI | 类型和 OpenAPI 友好、API 开发直接 | 鉴权、审核、迁移和业务边界仍需自己设计 |
| Django + DRF | 用户、管理后台、ORM 等集成较多 | 约定和学习内容更多，需评估是否适合小型 MVP |
| Flask | 核心轻量、自由度高 | 需要自行选择更多 schema、auth、迁移和工程组件 |
| Node/Nest 等 | JavaScript/TypeScript 全栈统一 | 团队技能、数据库和部署习惯需要确认 |

**重要**：在 ADR-0012 没有冻结之前，不能把 FastAPI 当成 MUST。新手应先读 ADR-0012，按团队实际技能和小型垂直切片结果决定。

### 13.3 为什么不把“技术选型”交给 AI

AI 可以提供候选资料，但不能独自决定：

- 团队是否维护得了；
- 供应商和许可证是否合规；
- 预算是否承受；
- 选型是否符合现有部署；
- 迁移和回滚成本是否可接受。

技术选型要写 ADR，包含背景、候选、证据、影响、迁移/回滚和复审日期。

## 14. 测试：先测最容易出事故的地方

### 14.1 测试金字塔

从快到慢、从局部到完整：

1. **单元测试**：状态转换、权限矩阵、schema、坐标和费用限制。
2. **合约测试**：OpenAPI、错误包、分页、幂等、版本兼容。
3. **集成测试**：真实临时 PostgreSQL、迁移、事务回滚、对象存储模拟、fake Provider。
4. **E2E 测试**：手机视口下浏览→投稿→审核→发布。
5. **安全测试**：上传、SSRF、限流、secret scan、依赖和许可证扫描。
6. **压测**：试点规模前建立 P50/P95、队列、数据库连接和费用基线。

### 14.2 新手第一次应该写哪些测试

推荐顺序：

1. 匿名用户不能创建草稿；
2. contributor 能创建自己的草稿；
3. contributor 不能编辑 `SUBMITTED_LOCKED` 草稿；
4. 提交同时创建版本、submission、review task 和 audit；
5. 两次使用同一个幂等键不会创建两个投稿；
6. reviewer 不能审核自己的投稿；
7. 未批准版本不能发布；
8. 公开接口不能读取 draft、quarantine、未发布版本；
9. 下线后匿名访问返回 404；
10. AI 只能写候选表，不能发布。

### 14.3 CI 绿灯不代表所有事情都验证了

CI 可以验证代码、契约和 fake provider，但通常不能证明：

- 真实地图供应商的商用条款；
- 真实 AI 的费用和数据保留策略；
- 公网备案完成；
- 生产环境配置正确。

这些要在联调记录、法务清单、运维 runbook 和发布 gate 中单独记录。

## 15. Vibe Coding：怎样安全地让 AI 帮你写代码

### 15.1 Vibe Coding 不等于“随便描述一句让 AI 全自动开发”

在本项目里，Vibe Coding 指：

- 人负责目标、范围、约束和验收；
- AI 负责检索、样板代码、测试草稿和局部实现；
- 人负责架构决策、权限、安全、内容审核和最终合并；
- 每个任务都有可复现的证据。

### 15.2 AI 开工前的五步

1. 读 `AGENTS.md`；
2. 读 `docs/PROJECT_CONTEXT.md`；
3. 读相关模块和 OpenAPI/ADR；
4. 确认只允许修改的目录；
5. 把验收命令写进任务说明。

### 15.3 推荐任务模板

```text
目标：实现 contributor 创建路线草稿 API。

范围：
- 允许修改 services/api/modules/routes/
- 允许新增对应单元测试和契约测试

不在范围：
- 不修改数据库迁移编号
- 不修改 publication、review、AI 模块
- 不添加依赖
- 不读取或写入真实密钥

依据：
- docs/api/openapi.yaml 中的 POST /api/v1/route-drafts
- ADR-0002、ADR-0003
- 当前 routes 模块的服务接口

验收：
- 匿名请求返回 401
- 登录用户只能成为新草稿 owner
- schema 错误返回统一 error 包
- 测试命令通过

必须回报：
- 改动路径
- 执行的命令和结果
- 未验证事项
- 可能的风险和回滚方式
```

### 15.4 AI 生成代码后的检查清单

- 是否修改了范围外文件？
- 是否偷偷新增依赖？
- 是否把权限判断只写在前端？
- 是否把数据库模型直接暴露为 API？
- 是否把异常吞掉并返回“成功”？
- 是否把密钥、生产日志或个人信息写进代码/测试？
- 是否绕过状态机直接更新 `published`？
- 是否有失败路径和权限负例？
- 是否执行了任务要求的命令？
- 能否解释每一段关键代码，而不是只说“AI 生成的”？

### 15.5 不要让 AI 做的事

- 不要让 AI 自己决定公开 API 的权限；
- 不要让 AI 自动生成并执行生产数据库迁移；
- 不要把真实 API key、用户隐私和审核材料粘贴给通用模型；
- 不要让 AI 直接合并 PR 或发布内容；
- 不要把模型返回的“测试通过”当作命令证据；
- 不要为了“顺手优化”修改其他模块。

## 16. 团队协作：8 个人怎样共同做一个产品

### 16.1 为什么按业务模块分组，而不是简单分前端组和后端组

如果一组只写页面、另一组只写后端，双方会互相等待，且业务规则没人真正负责。

当前建议：

**A 组：用户体验与内容贡献**

- A1：H5 浏览和路线详情；
- A2：路线编辑和投稿；
- A3：文化节点和媒体；
- A4：身份和个人中心。

**B 组：治理与平台能力**

- B1：审核和发布后台；
- B2：API、数据库和迁移；
- B3：地图和导航 Adapter；
- B4：AI、任务、质量、CI 和观测。

每个人有一个主 owner 和一个 backup。A/B 各有集成联系人，lead 处理跨组冲突和 ADR。

### 16.2 协作规则为什么重要

- **接口先行**：没有 API/schema 和验收例，不开始跨组实现；
- **写边界**：每个 PR 尽量只改自己的模块和测试；
- **数据库单写者**：迁移编号由指定 owner 管理；
- **禁止直接改 main**：通过分支和 PR 合并；
- **代码发布与内容发布分离**：开发者不能直接 SQL 改公开状态；
- **证据回报**：完成报告必须写命令、结果和未验证项。

这些规则不是为了增加流程，而是为了让 AI 生成的代码不会互相覆盖和漂移。

### 16.3 只有 4 个人时怎么办

仍然保留模块边界：

- P1：产品、架构、契约、审核规则；
- P2：H5 浏览、编辑、投稿和管理端页面；
- P3：API、数据库、身份、RBAC、状态机；
- P4：地图、AI Adapter、任务、CI、观测、部署。

顺序是先由 P1+P3 冻结契约和状态机，再让 P2/P4 并行。人少时可以减少路线字段，但不能省掉审核、审计、备份和限流。

## 17. 从零开始的开发路线

### 阶段 0：基础和契约

目标：让新成员可以启动项目，且团队知道边界。

- 建立独立仓库；
- 写 `AGENTS.md`、`PROJECT_CONTEXT.md`；
- 完成 ADR-0001～0004；
- 比较并冻结 ADR-0011/0012；
- 建立 OpenAPI 骨架、健康检查、数据库迁移；
- 写四套状态机的单元测试；
- 做 H5 shell 和匿名路线列表 fixture。

DoD：空库迁移成功、CI 绿、越权和非法状态测试通过、无密钥、旧 Demo 未被修改。

### 阶段 1：MVP 纵向闭环

目标：走通匿名浏览→登录→创建草稿→投稿→审核→发布→匿名浏览→下线。

- 路线和节点；
- 投稿快照；
- 审核队列和 diff；
- 发布/下线；
- 审计、媒体授权、限流和备份；
- fake 地图和 fake AI Provider。

DoD：每个状态有权限负例，每个高风险动作有审计，数据库从零可重建，E2E 和回滚演练通过。

### 阶段 2：国内公网试点硬化

- 核验域名、TLS、备案和供应商条款；
- 小额真实地图/AI 配额；
- 费用告警、限流、脱敏和人工 fallback；
- 上传扫描、投诉/下线和隐私流程；
- 压测、备份恢复和密钥轮换。

### 阶段 3：体验和运营

在有真实指标后再做搜索、收藏、反馈、申诉、审核 SLA 和推荐。

### 阶段 4：离线和智能化

只有在数据许可、容量、隐私和用户需求都明确后，再做离线地图、离线包、多模型和复杂路径优化。

## 18. 新手的第一个 Sprint：不要从首页开始

第一个 Sprint 的目标不是“首页看起来很漂亮”，而是完成最小纵向链路。

推荐执行顺序：

### 第 1 天：读文档和跑环境

- 读本手册和原规范；
- 确认仓库和旧 Demo 的边界；
- 运行 README 中的启动命令；
- 确认数据库和测试命令；
- 不要先写业务代码。

### 第 2 天：契约和数据

- 阅读 OpenAPI；
- 确认角色和四套状态机；
- 写一个创建草稿 API 的失败测试；
- 了解迁移和回滚。

### 第 3 天：完成一条后端纵向片段

- 创建草稿；
- 保存节点和来源；
- 提交固定快照；
- 创建投稿、审核任务和审计；
- 测试并发和幂等。

### 第 4 天：接入页面和审核

- H5 展示公开 fixture；
- 用户创建并提交草稿；
- reviewer 领取并退回/通过；
- editor 发布。

### 第 5 天：端到端验证

- 匿名再次看到已发布路线；
- 下线后不能看到；
- 跑全部测试、CI 和 smoke；
- 写失败路径、未验证项和回滚记录。

### 新手完成标准

你不是“写了很多代码”才算完成，而是能回答并证明：

- 这条路线的公开版本是哪一个？
- 审核员批准的是哪一个 hash？
- 谁可以发布？谁不可以？
- AI 生成的内容怎样进入草稿？
- 用户重复点击投稿会怎样？
- 两个人同时编辑会怎样？
- 下线后公共缓存怎样失效？
- 哪些事情还没有真实验证？

## 19. 常见错误和排查方法

### 错误 1：把旧旅行规划 Demo 当成新平台基础

**问题**：旧项目只有本机演示能力，不具备账号、社区投稿、审核和公网平台能力。

**处理**：新平台独立建仓库；旧项目只参考交互和失败边界。

### 错误 2：页面上没有按钮就以为安全

**问题**：攻击者可以直接调用 API。

**处理**：后端执行认证、角色、对象所有权和状态校验，并写权限负例。

### 错误 3：用一个 `status` 表示全部状态

**问题**：审核通过不一定已经发布，审核任务完成也不代表公开版本存在。

**处理**：使用四套正交状态机。

### 错误 4：直接修改已批准版本

**问题**：无法证明审核员批准了哪段内容。

**处理**：从固定版本 fork 新草稿，重新生成 hash 和投稿。

### 错误 5：把 AI 文本当作来源

**问题**：模型可能产生错误文化信息，且无法证明来源。

**处理**：来源必须由人或可靠资料补充；AI 只做候选；作者、reviewer、editor 三道动作都留痕。

### 错误 6：把访问顺序连线说成最短导航

**问题**：连线不等于道路级路径，也可能涉及供应商许可。

**处理**：明确展示类型；无证据时只说节点顺序或外部导航入口。

### 错误 7：AI 修改了很多无关文件

**问题**：边界漂移，审查困难，容易破坏别的模块。

**处理**：任务中写 `范围` 和 `不在范围`，提交前检查 `git diff --stat` 和改动路径。

### 错误 8：测试只测成功路径

**问题**：越权、重复提交、过期版本、上传恶意文件等风险都未覆盖。

**处理**：每项功能至少补一个权限负例、一个状态负例和一个重复/并发场景。

### 错误 9：把“待验证”写成确定结论

**问题**：可能导致违规采购、费用失控或错误上线。

**处理**：在 PR、ADR、发布清单中明确写“未验证”，指定 owner 和验证日期。

## 20. 一页式开发检查表

### 开始任务前

- [ ] 我读了 `AGENTS.md` 和 `PROJECT_CONTEXT.md`。
- [ ] 我知道当前任务的模块 owner 和修改范围。
- [ ] 我找到了对应 OpenAPI、ADR 和状态机规则。
- [ ] 我知道哪些是 MUST、SHOULD、LATER。
- [ ] 我没有把假设当成事实。

### 写代码时

- [ ] 业务规则在后端，不只在前端。
- [ ] 没有跨模块直接读写别人的 ORM/表。
- [ ] 版本、权限、幂等和状态转换有明确处理。
- [ ] 外部地图/AI 返回值经过 schema、超时和错误校验。
- [ ] 没有把密钥、个人信息和生产数据放入代码或 prompt。

### 提交前

- [ ] 只修改了任务允许的文件。
- [ ] 有成功测试和失败/越权测试。
- [ ] 迁移可在空库重放，必要时有回滚说明。
- [ ] 运行了 lint、typecheck、unit、integration 或对应最小命令。
- [ ] PR 写明改动路径、命令结果、未验证项和风险。

### 发布前

- [ ] 公开接口只返回当前 `PUBLISHED` 版本。
- [ ] 管理 API 不能匿名访问。
- [ ] AI 内容不是直接发布结果。
- [ ] 上传媒体已扫描、授权并清理元数据。
- [ ] TLS、密钥、限流、备份、恢复和审计已检查。
- [ ] 地图/AI 供应商条款、费用和合规事项有结论。

## 21. 给 AI 的最短提问模板

当你不知道怎样向 AI 提问时，使用下面的结构：

```text
我正在做 CulturalWalk 的【模块名称】。

目标：
【只写一个可验收目标】

请先阅读：
- AGENTS.md
- docs/PROJECT_CONTEXT.md
- 【相关 ADR】
- 【相关 OpenAPI 路径】

允许修改：
- 【目录/文件】

禁止修改：
- 【其他模块、迁移、密钥、生产数据】

必须遵守：
- 【角色权限】
- 【状态机】
- 【幂等/版本/审计】

请先给出：
1. 你理解的目标；
2. 将修改的文件；
3. 验收命令；
4. 可能风险。

确认后再实现。完成后只报告：改动路径、命令结果、未验证项和回滚方式。
```

这个模板的核心不是文字本身，而是强制 AI 先理解边界，避免“先改了再解释”。

## 22. 术语表

| 术语 | 解释 |
|---|---|
| H5 | 移动浏览器中的网页应用 |
| MVP | 最小可行产品，用最少功能验证真实需求 |
| API | 程序之间调用能力的接口 |
| OpenAPI | 用机器可读格式描述 HTTP API 的标准 |
| DTO | API 对外传输的数据对象，不等于数据库表 |
| ORM | 用代码对象访问数据库的工具 |
| Migration | 数据库结构版本变更脚本 |
| Transaction | 一组操作全部成功或全部回滚 |
| Optimistic Lock | 用版本号检测并发修改 |
| Idempotency | 同一请求重复执行不会产生额外副作用 |
| RBAC | 基于角色的访问控制 |
| Audit | 记录谁在何时对哪个对象做了什么 |
| Snapshot | 提交或审核时冻结的内容版本 |
| Hash | 用于识别内容是否发生变化的摘要值 |
| Fork | 从旧固定版本复制一个新的可编辑副本 |
| Provider | 外部地图、AI 等服务供应商接口 |
| Adapter | 把外部供应商接口转换为内部统一接口的代码 |
| Fixture | 测试中预先准备的固定数据或返回值 |
| E2E | 从用户界面到后端和数据库的端到端测试 |
| CI | 每次提交自动运行的检查流程 |
| CD | 自动或半自动部署流程 |
| ADR | Architecture Decision Record，架构决策记录 |
| DoD | Definition of Done，完成定义 |
| PR | Pull Request，提交代码供审查和合并 |
| Vertical Slice | 从界面到数据完整贯穿的一条可运行业务链路 |
| Provenance | 内容来源、生成过程和人工决策记录 |
| CRS/datum | 坐标参考系和地理基准 |
| P95 | 95% 请求耗时不超过的性能指标 |
| SSRF | 服务器端请求伪造，诱导服务器访问不应访问的地址 |

## 23. 最后的学习建议

如果你是完全的新手，不要试图一次读懂 864 行架构规范，也不要一次让 AI 生成整个系统。建议采用这个节奏：

1. 先理解一个用户故事：创建草稿。
2. 再理解一个对象：`route_draft`。
3. 再理解一个接口：`POST /api/v1/route-drafts`。
4. 再理解一个权限负例：匿名用户不能创建草稿。
5. 再理解一次提交事务：版本、投稿、任务、审计一起成功或回滚。
6. 再把这条链路接到 H5 页面。
7. 最后再接入真实地图和 AI。

**先把“小闭环”做正确，再扩大功能。**这正是当前规范选择模块化单体、API-first、状态机、Adapter、人工审核和 Vibe Coding 护栏的共同原因。

如果你想确认自己是否真正理解，可以尝试用自己的话回答：

> “用户提交路线以后，谁能修改它？审核员批准的是哪一版？AI 在哪里可以帮忙？哪一步必须由人做？如果用户连续点击两次，会不会产生两个投稿？路线下线后匿名用户还能看到什么？”

能清楚回答这些问题，并用测试证明答案，就已经从“会调用 AI”进入了“会参与软件开发”。
